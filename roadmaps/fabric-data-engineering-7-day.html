You already did the core trick: a notebook wrote a Delta table into a lakehouse, and it landed in OneLake — one store for the whole tenant, as open Delta/Parquet. Every engine reads it with zero copies: T-SQL via the SQL endpoint, DAX via Direct Lake, Spark, external tools via the OneLake APIs. Traditional stacks copy data between a lake, a warehouse and a BI model — three copies, three refresh windows, three chances to disagree. Fabric splits storage (OneLake) from compute (Spark, T-SQL, KQL, DAX, Power Query); every item in the portal is just one of those engines pointed at the same store.

The distinction people get wrongA lakehouse's SQL endpoint is read-only. Need write-back through SQL? That's a Warehouse, not a lakehouse — the most common early Fabric mis-pick.
For your orgWhere does your organisation copy the same numbers between systems today? Each hop is a refresh window and a reconciliation argument — that list is your business case.

Instinct says "write a pipeline to copy it in." In Fabric that should be your third instinct. The first question is always: do I need a copy at all? Every copy you avoid is a schedule you don't maintain and storage you don't pay for.

Four things hold tables in Fabric. They aren't interchangeable, and picking correctly is most of what "architecture" means day to day.

StoreWrite withChoose it when
LakehouseSpark, pipelines, dataflowsFiles and tables, Python/Spark, semi-structured data. SQL endpoint is read-only.
WarehouseT-SQL (full DML)SQL-first team, multi-table transactions, stored procedures.
Eventhouse / KQLEventstream, KQLHigh-volume time-series, logs, telemetry.

Python team → Lakehouse. SQL team → Warehouse. Events → Eventhouse. App writes → SQL database. All four end up as Delta in OneLake — the choice is about authoring experience and write pattern, not where the bytes go.

What Delta actually is — the 60-second version

A Delta table is Parquet files plus a transaction log (_delta_log) recording every commit. That log is what gives you ACID transactions, time travel, and safe concurrent writes on plain cloud storage.

  • Deletes aren't immediate — old files linger until VACUUM, which also caps how far back you can time-travel.
  • V-Order is Fabric's write optimisation, making Parquet much faster for VertiPaq/Direct Lake reads. On by default.
  • Time travel now works from the SQL analytics endpoint too, via a TIMESTAMP clause.
  • Don't partition small tables — under a few GB it usually recreates the small-file problem.
# run these on the table you already built
spark.sql("DESCRIBE HISTORY your_table").show(10, truncate=False)   # every commit
spark.sql("OPTIMIZE your_table")                                  # compact small files
spark.sql("DESCRIBE DETAIL your_table").show(truncate=False)      # file count & size

# read it as it was 3 versions ago
df = spark.read.format("delta").option("versionAsOf", 3).table("your_table")

Your notebook works. The gap to running unattended at 3am is four things: where dependencies come from, how it gets its inputs, how it loads data the second time, and what it costs.

1. Environments

An Environment holds Spark runtime, libraries and config, attached to notebooks or Spark job definitions. It's how you stop %pip install in cell one — and the honest answer to "why did it work yesterday?"

2. Parameters

Mark a cell as the parameter cell (cell menu → Toggle parameter cell). A pipeline or another notebook overrides those values when calling it — the single change that turns a script into a component.

# parameter cell — defaults for interactive runs, overridden by the caller
load_date = "2026-08-01"
source_system = "sap"
full_reload = False

# elsewhere: chain notebooks and read pipeline values
import notebookutils
notebookutils.notebook.run("transform_silver", 300, {"load_date": load_date})
notebookutils.notebook.exit("success")   # returned to the calling pipeline

3. Incremental loads

Loading changes instead of rewriting the table is the beginner→practitioner jump. Delta's MERGE upserts in one atomic commit:

from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "silver_customer")
(target.alias("t")
  .merge(updates.alias("s"), "t.customer_id = s.customer_id")
  .whenMatchedUpdateAll()
  .whenNotMatchedInsertAll()
  .execute())

Turn on .option("mergeSchema", "true") when upstream columns legitimately change — but that makes schema drift silent. Usually on in bronze, off in gold.

4. Cost

Everything in Fabric draws from one shared Capacity Unit pool — Spark, SQL, pipelines, Power BI. An idle attached Spark session is the classic silent burner. Autoscale billing for Spark lets Spark jobs bill serverlessly instead of competing for capacity.

Do this — 6 minutes

Cost trapAn attached notebook session left open all afternoon burns capacity doing nothing. On a shared F-SKU, one careless session can throttle everyone else's reports.
For your orgFind out what SKU your organisation runs, whether it's shared across teams, and who watches the metrics app. Often the honest answer is "nobody" — an open lane for you.

Medallion architecture is three layers, and the value is entirely in not skipping one:

  • Bronze — raw, no cleaning, append-only with load timestamp + source. Lets you rebuild everything without re-hitting the source.
  • Silver — cleaned and conformed: types fixed, duplicates resolved, keys standardised.
  • Gold — shaped for consumption, modelled as a star schema: fact tables of numbers, dimensions you slice by.

Why star schema, still, in 2026? Because VertiPaq — the engine behind every Power BI model — is built for it. One wide flat table compresses worse, makes measures ambiguous, and scans more per filter. On Power BI, gold-as-star-schema is the difference between a report that returns instantly and one that doesn't.

Materialized lake views

Instead of hand-orchestrating bronze→silver→gold refreshes, materialized lake views let you declare the transform and let Fabric manage materialisation and lineage. Lineage now spans layers and workspaces: one schedule on gold cascades back through silver and bronze automatically.

Direct Lake — and the trap that will bite you

A Direct Lake model reads Delta from OneLake straight into memory — import speed, no refresh, always current. It's why gold-layer modelling matters so much.

The Direct Lake trapViews can't be framed by Direct Lake — add one and the entire model falls back to DirectQuery, not just that table. Reports get slower and nobody can see why. Fix: materialise the view as a Delta table.

You've connected a workspace to Git — further than most Fabric users get. Here's the rest of the lifecycle, and what Git doesn't solve.

The three pieces

  • Git integration — source of truth for item definitions (notebooks, pipelines, models, reports). Branch out to a new workspace gives each feature its own sandbox.
  • Deployment pipelines — promote items dev→test→prod, with deployment rules swapping connections/parameters per stage.
  • Variable libraries — per-stage values (connections, item references, lakehouse IDs) that pipelines and notebooks read, so nothing's hardcoded. Recently added connection and item reference types.

What Git does not capture

  • Data — Git versions definitions, not table contents.
  • Shortcuts — not carried by deployment pipelines; recreate or automate them.
  • Item bindings — a notebook's default lakehouse, a pipeline's connection — exactly what variable libraries solve.
  • Capacity & workspace settings — live outside the repo.

For automation beyond the UI: the Fabric REST API, the Fabric CLI, and the fabric-cicd Python library. Knowing they exist is the difference between "we click Deploy" and "we have a release process."

Do this — 6 minutes

Where this makes you valuableMost orgs adopting Fabric have a lifecycle problem, not a technology problem: one workspace, one person, nothing promotable safely. Introducing branch-per-feature, variable libraries and a promotion path outweighs any single pipeline you'll write.

A pipeline nobody consumes is a cost centre. Fabric has five distinct ways to serve what you've built.

  • Semantic model + report — the default. Direct Lake over your gold layer.
  • SQL endpoint — anyone with SQL or Excel queries it directly. Underused; often the fastest way to make analysts happy.
  • Data agents — an NL agent grounded in your data (lakehouse, warehouse, model, eventhouse, DB). GA, now with Git and deployment-pipeline support. Quality depends entirely on how well your gold layer is modelled and named.
  • Activator — rules on streams or visuals that fire Teams, email or Power Automate on a condition. Turns data into action, not a dashboard nobody opens.
  • Fabric Apps — new in 2026, real web apps on Fabric data with Entra auth built in.

Governance, briefly — what makes any of it trustworthy

  • Domains group workspaces by business area, with their own admins — avoids one flat list of 400 workspaces.
  • OneLake catalog is how people find data; endorsement (Promoted / Certified) says which copy to trust.
  • Purview brings sensitivity labels and lineage across the estate.
  • Workspace roles plus OneLake security decide who sees what — mirrored data now carries security through shortcuts downstream.

For your orgThe fastest credibility win is rarely a new pipeline — it's taking something people already wait for (a manual extract, an emailed spreadsheet) and making it a governed table plus an alert.
